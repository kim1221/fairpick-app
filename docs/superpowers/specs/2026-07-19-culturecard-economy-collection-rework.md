## 2. 경제 모델

### 2.1 단위경제 표

| 항목 | 현행 | 개편 후 |
|---|---|---|
| 광고 1회 → 티켓 | 1~3개 가중랜덤(기대 1.65) | **1개 고정** |
| 교환 단위 | 10티켓 = 1교환 | 동일 |
| 교환당 광고 횟수 | 기대 ~6.1회 | **10회 고정** |
| 교환 금액 | 콘솔 설정(현행 고정) | **랜덤, 평균 20원** (10~20원 다수, 50원 가끔, 큰 금액 희귀 꼬리) |
| 광고당 기대 지급비용 | ~3.3원 (평균 20원 가정 시) | **2.0원** |
| 일일 오픈 캡 | 50 고정 | **min(50, 지역 동적 캡)** |
| 일일 티켓 한도 | 150 (`50×3`) | **오픈 캡과 동일** (1:1이므로 별도 한도 사실상 불필요, 하드 상한 50 유지) |
| 유저 하루 최대 지급 | — | 50오픈 → 5교환 → **평균 100원/유저/일** (지역 캡이 낮으면 그 이하) |

서프라이즈의 이동: 티켓 수 랜덤(제거) → **카드 내용물 + ? 슬롯 + 컬렉션 진행 + 포인트 뽑기 랜덤 금액**이 담당.

### 2.2 지역 풀 기반 동적 오픈 캡 — 구체 설계

목적: 신선 카드가 소진된 지역에서 전국 폴백 카드를 무한 공급하는 대신, 그날 캡을 낮추고
"오늘의 카드는 여기까지, 내일 새 카드" 프레이밍으로 끊는다. 캡은 **서버 권위**로 강제한다.

실측 참고(7일 노출 쿨다운 기준 지속 가능 소진율): 서울 ~30장/일(활성 1,156, 주간신규 +338),
경기 ~8, 부산 ~4, 대구 이하 1~3장.

**공식**

```
F_fresh  = 유저 기준 신선 풀 크기
         = 유저 위치 반경(기존 NEARBY_RADIUS_STEPS_M 최대 50km) 내 활성 이벤트 중
           (이미 연 카드 제외) AND (최근 7일 노출 쿨다운 제외) 인 이벤트 수
           — /v2/today의 후보 수집 eligibility 필터와 동일 조건. 위치 없으면 전국 폴백 풀 기준.

C_day    = F_fresh ≥ CANDIDATE_LIMIT(300) 인 경우      → DAILY_OPEN_LIMIT(50)   … "풀 충분"
           그 외                                        → clamp(⌊F_fresh / ROTATION_DAYS⌋, CAP_FLOOR, 50)

ROTATION_DAYS = 7   (노출 쿨다운 7일과 정합 — 오늘 풀의 1/7만 소진하면 일주일 회전 가능)
CAP_FLOOR     = 3   (오늘의 3장 경험은 풀이 3장 이상이면 항상 보장. F_fresh < 3이면 C_day = F_fresh,
                     0이면 기존 pool_empty 상태)
```

검산: 서울 신규 유저 F≈1,156 → 풀 충분 → 캡 50. 서울 헤비 유저(누적 1,000장 오픈) F≈156 → 캡 22.
부산 F≈28 → 캡 4. 대구 F≈10 → 캡 3(플로어). 실측 지속 가능 소진율과 자릿수가 맞는다.
ROTATION_DAYS·CAP_FLOOR는 §9 측정 후 튜닝 노브.

**하루 안 고정 규칙(중요)**

- 캡은 그날 첫 `/v2/today` 계산 시 확정해 저장하고(`user_tickets.daily_open_cap`, `daily_open_cap_date`),
  같은 날 재계산 시 **`max(저장값, 신규 계산값)`으로 상향만 허용**한다.
  - 이유 1: F_fresh는 유저가 오늘 카드를 열수록 줄어든다 — 재계산 시 캡이 낮아지면
    "뽑는 중에 캡이 줄었다"는 경험이 된다.
  - 이유 2: 유저가 낮은 캡 지역 → 서울로 이동하면 캡이 오르는 건 자연스럽다(상향만 반영).
  - 위치 스푸핑으로 캡을 올려도 상한 50 + 티켓 가치 고정이라 이득이 제한적(§7).
- 오픈 시(`grantTicketsForEvent`) `dailyOpenCount ≥ C_day`이면 `DAILY_OPEN_LIMIT_REACHED`(429) —
  기존 에러 코드 재사용, 응답에 동적 캡 값 포함.

**프레이밍(응답 계약)**: `/v2/today` 응답의 `dailyOpenLimit`을 동적 값으로 내리고,
`openCap: { base: 50, effective: n, reason: 'daily_max' | 'regional_pool', regionLabel }`을 추가한다.
`reason='regional_pool'`로 캡에 닿으면 클라는 "오늘 {지역}의 카드는 여기까지예요.
내일 새 카드가 도착해요"로 표기(한도 페널티가 아니라 지역 희소성 프레이밍).

### 2.3 티켓 고정 1개

- `backend/src/services/ticketGrant.ts`의 `randomTickets()` 제거, `earned = 1` 고정.
- `DAILY_TICKET_LIMIT = DAILY_OPEN_LIMIT`(50)로 축소. 1:1이므로 오픈 캡이 실질 한도이고
  티켓 한도는 이중 안전장치로만 남는다. `DAILY_LIMIT_REACHED` 경로·문구는 유지(도달 사실상 불가).
- 클라 reveal 연출에서 "티켓 n개!" 랜덤 강조 제거 → "티켓 +1" 고정 표기 + 티켓 게이지(n/10) 진행 강조.

### 2.4 교환 = "포인트 뽑기" + 서버 권위 랜덤 금액 (✅ 방식 A 확정, 2026-07-20 G1)

- 2-step fail-closed 흐름(`POST /exchange` pending → SDK `grantPromotionReward` → `POST /exchange/confirm`)은 그대로.
- **금액은 서버가 추첨한다(서버 권위)**: "최대 금액" 방식 프로모션은 개발자가 SDK에 보낸 `amount`가
  그대로 지급되고 콘솔 등록액은 상한 역할(커뮤니티 공식 답변). 이를 이용해:
  1. `POST /exchange`(pending 생성) 시 서버가 분포에서 금액 추첨 → `user_ticket_exchanges.amount`에 저장
     (기존 하드코딩 1 플레이스홀더의 의미를 "지급 원화 금액"으로 승격 — 과거 4건도 실지급 1원이라 정합.
     신규 컬럼·마이그레이션 불필요) → 응답에 `amount` 포함.
  2. 클라가 그 `amount`로 `grantPromotionReward` 호출(현행 `amount: 1` 하드코딩 제거).
  3. `confirm`은 기존대로 — 서버가 이미 금액을 알므로 클라 보고 불필요. 응답에 `amount` 포함(연출용).
- **분포(평균 20.0원, 꼬리)**: 10원 50% · 15원 20% · 20원 12% · 30원 10% · 50원 6% · 100원 1.6% · 500원 0.4%.
  상수 테이블로 정의(튜닝 노브). 서버 가드: 추첨값은 테이블 밖 값 불가.
- **콘솔(G5, 사용자)**: 프로모션 최대 금액을 분포 최대치(500원) 이상으로 설정. 랜덤 기능 불필요.
- UI 브랜딩: 티켓 10개 도달 시 CTA를 **"포인트 뽑기"**로. "광고 10번 = 포인트 뽑기 1번"이 홈에서 읽히게
  티켓 게이지를 10칸으로 표기. 금액 표기는 과장 금지 — "최대 OOO원!" 강조 대신 평균·범위 중심(§7).

## 3. 홈 뽑기 플로우 재설계 (연속 뽑기)

### 3.1 유저플로우

```
진입(/)
 └─ 상단: 오늘 진행 게이지(openCount / 동적캡) + 티켓 게이지(n/10 → "포인트 뽑기")
 └─ 봉인 슬롯 3개: [카테고리 A] [카테고리 B] [ ? 미스터리 ]
      │  (카테고리 라벨·티저 카피는 현행 toLockedPreview 유지, ? 슬롯만 카테고리 은닉)
      ▼ 슬롯 선택 → "광고 보고 컬처카드 공개하기"
 광고 load→loaded→show → userEarnedReward → POST /v2/open (현행 로직·워치독 그대로)
      ▼
 카드 공개(reveal)
   ├─ 티켓 +1 (고정)
   ├─ [신규] 컬렉션 슬롯 채움 연출: 이 카드가 채운 세트 슬롯이 있으면 "『성수 컬렉션』 3/5 채움" 배너
   ├─ [신규] ? 슬롯 산출물이면 히든/탐험 프레임 연출
   └─ CTA: [다음 카드 뽑기]  [상세 보기]  [저장]
      ▼ "다음 카드 뽑기" (남은 캡 있음)
 슬롯 화면 복귀 — 열린 슬롯은 서버가 즉시 재보충(현행 refresh 동작 재사용) → 루프 반복
      ▼ 캡 도달
 종료 화면: reason='regional_pool'이면 "오늘 {지역}의 카드는 여기까지예요. 내일 새 카드가 도착해요"
           reason='daily_max'이면 현행 "오늘 공개 완료" 문구 → [컬렉션 보기] CTA
```

- 루프는 **항상 명시적 버튼으로만 진행**한다. reveal 후 자동으로 다음 광고를 로드-표시하지 않는다
  (광고 프리로드는 현행처럼 백그라운드 load만, show는 유저 액션 필수 — 다크패턴 회피, §7).
- 광고 모듈(`loadFullScreenAd`/`showFullScreenAd`, attemptId 로깅, show 워치독, fail-closed)은
  **건드리지 않는다**. 재설계 범위는 슬롯 프레젠테이션·reveal 후 내비게이션·진행 게이지다.

### 3.2 "?" 미스터리 슬롯 설계

- 구성: `TODAY_CARD_COUNT=3` 유지. 슬롯 2개 = 기존 카테고리 슬롯(일별 셔플 + 유저 선택 가능),
  슬롯 1개 = `slotType='mystery'` — 카테고리·티저를 은닉하고 "?" 프레젠테이션.
- 서버 공급 규칙(? 슬롯 후보 선정, 서버 권위 — 우선순위 확률은 튜닝 노브):
  1. **컬렉션 어시스트 (60%)**: 유저가 진행 중(1슬롯 이상 채움)인 세트의 빈 슬롯 조건에 맞는 카드.
     "?에서 나온 카드가 마침 세트 조각"이라는 설계된 우연 — 컬렉션 완성 동력.
  2. **탐험 (25%)**: 유저 취향 상위 카테고리가 아닌 카테고리의 고buzz 카드(안 가본 장르 노출).
  3. **와일드 (15%)**: 완전 랜덤(지터 상위).
- **히든 카드**: ? 슬롯에서만 등장하는 특수 프레임. 조건 = buzz_score 상위(예: 지역 상위 10%) 또는
  세트의 마지막 남은 조각. 데이터는 동일 실데이터이고 프레임·연출·컬렉션 "히든 발견" 표기만 특별.
  희귀 배지(§4.4)의 진행 조건으로 쓴다.
- 취향 신호: ? 슬롯으로 연 카드도 기존 taste 신호(열기=1)에 동일 포함(단순 유지).
- 검수 관점: ? 슬롯 결과는 실물 금전 가치가 없고(카드 공개·수집 전용) 티켓은 항상 1개 고정이므로
  확률형 아이템 규제·과장 광고 이슈 면적이 없다.

### 3.3 백엔드 정합

- `user_daily_card_slots`에 `slot_type('category'|'mystery')` 컬럼 추가. 배정·핀 고정·재보충은
  기존 슬롯 로직(`assignTodayCardsToSlots` 계열) 확장으로 처리.
- `/v2/today`의 `lockedCards[]`에 `slotType` 추가. mystery 카드는 `category`·`teaserEyebrow` 등
  내용 단서를 응답에서 제거(카드 토큰·visualSeed만 유지).
- `/v2/open` 응답에 `reveal: { slotType, hidden: boolean }`, `collectionProgress[]`(§5.2) 추가.

## 4. 테마 컬렉션 (핵심 신기능)

### 4.1 개념

- 세트 = "성수 컬렉션(팝업2+전시1+공연1)", "장마철 실내 전시 4곳" 같은 수집 미션.
- 미공개 슬롯은 **실루엣 + 힌트**만 노출(예: 흐려진 포스터 실루엣 + "성수의 어느 F&B 팝업").
  카드 공개 희소성을 유지하면서 미공개 이벤트를 티저로 활용한다.
- **내가 연 카드가 조건에 맞으면 슬롯을 자동으로 채운다.** 유저의 별도 쓰기 액션 없음
  (클라 쓰기 API 없음 → 위변조 면적 최소).
- 완성 보상 = **배지/특별 스탬프** (티켓·실돈 아님 — 검수 안전).

### 4.2 슬롯 매칭 규칙

- 슬롯은 특정 이벤트 고정이 아니라 **조건 매칭**: `match_rule = { category, regionScope, tags? }`
  (예: category=팝업 AND region LIKE 성수). 조건 기반이라 완성이 운에만 의존하지 않고,
  ? 슬롯 컬렉션 어시스트(§3.2)와 결합해 달성 가능성을 서버가 조절한다.
- 실루엣 이미지는 슬롯 조건에 맞는 **미공개 이벤트 중 하나를 대표(teaser_event_id)로 지정**해
  실루엣 처리한다(티저용일 뿐, 채움 인정은 조건 매칭 기준).
- 인정 범위: **세트 발행 시각 이후에 연 카드만** 카운트(소급 인정 없음 — 발행 즉시 자동완성 방지,
  매일 여는 동기 유지).
- 한 카드는 여러 세트의 슬롯을 동시에 채울 수 있다(중복 허용). 한 세트 안에서는 1카드 = 1슬롯.
- 매칭 시점: `/v2/open` 트랜잭션 안에서 활성 세트의 빈 슬롯과 대조 → `user_collection_progress` 기록
  → 채움/완성 결과를 open 응답에 실어 reveal 연출에 사용.

### 4.3 세트 자동 생성 룰 (수동 큐레이션 없음)

- 축: `region × main_category × 시즌/태그(derived_tags, buzz_score)`.
- 템플릿 4종(초기):
  | 템플릿 | 예시 | 구성 룰 |
  |---|---|---|
  | 동네 세트 | "성수 컬렉션" | 같은 세부 지역의 카테고리 횡단 4슬롯(팝업2+전시1+공연1) — 유저 선택 다변화 유도 |
  | 시즌 세트 | "장마철 실내 전시 4곳" | 시즌 키워드 × derived_tags 매칭 4슬롯 (기간 한정 = 희귀 배지) |
  | 딥다이브 세트 | "이번 달 서울 전시 5곳" | region × 단일 카테고리 5슬롯 |
  | 버즈 세트 | "지금 뜨는 팝업 4곳" | buzz_score 상위 × 카테고리 4슬롯 |
- 생성 배치: **주 1회(월요일 KST)**. 활성 풀 상위 지역별로 템플릿 실행 → 조건 만족 이벤트가
  (슬롯 수 × 2) 이상 확보될 때만 발행(달성 가능성 담보). 이벤트 자격: 활성, `end_at`이 세트 만료 이후,
  이미지 있음, 데이터 품질 good 이상.
- 노출 상한: 유저에게 동시 노출되는 활성 세트 = 지역 세트 최대 3개 + 전국/시즌 세트 1~2개
  (과다 노출로 미션 피로 방지).
- 세트 수명: `expires_at = 발행 + 28일`. 만료 시 상태 `ended` — 완성 못 해도 페널티 없음,
  진행 기록은 컬렉션 아카이브에 남는다.
- 구성 이벤트 만료/삭제 처리:
  1. 빈 슬롯의 조건을 만족하는 활성 이벤트가 남아 있으면 그대로 유지(조건 매칭이라 스왑 불필요,
     teaser_event_id만 활성 이벤트로 교체).
  2. 조건 만족 활성 이벤트가 0이 되면: 우선 조건 완화 없이 **세트 조기 마감**(`ended_early`) —
    진행 중 유저에게 "이번 세트는 여기서 마감됐어요" 표기, 자동 완성 인정은 하지 않는다
    (배지 인플레이션 방지). 단 1슬롯만 남은 유저가 있으면 마감 전 ? 슬롯 어시스트가 우선 공급을 시도한다.

### 4.4 배지 체계

- **세트 배지**: 세트 완성 시 세트 고유 배지 1개(지급 멱등: unique(user_id, badge_key)).
  시각물은 세트 구성 카드의 콜라주/씰 형태 — G2에서 확정.
- **등급**: 일반(상시 템플릿) < 시즌 한정(기간 한정 세트) < 히든(히든 카드 슬롯을 포함해 완성).
  등급 명칭·비주얼은 G2.
- **마일스톤 메타 배지**(소량): 세트 3개 완성, 10개 완성, 히든 카드 5회 발견 등.
- 배지는 티켓·포인트로 환전 불가. 컬렉션 탭 '배지장'에 영구 보관 + 방문 도장(기존)과 나란히
  "문화 이력"을 구성한다.

### 4.5 컬렉션 탭 통합 유저플로우

```
컬렉션 탭(/passport) 진입
 └─ [신규] 최상단 "테마 컬렉션" 섹션: 진행 중 세트 카드 캐러셀
      (세트명 + 진행 n/m + 채운 카드 썸네일 + 빈 슬롯 실루엣 미리보기)
      ▼ 세트 선택
 세트 상세 (신규 화면)
   ├─ 채운 슬롯: 실제 카드(기존 컬렉션 카드 스타일)
   ├─ 빈 슬롯: 실루엣 + 힌트 텍스트("성수의 어느 F&B 팝업")
   ├─ 남은 기간(D-n) + "오늘 카드를 열면 채워질 수 있어요" 안내
   └─ 완성 시: 배지 수여 연출 → 배지장 링크
 └─ [신규] "배지장" 섹션(획득 배지 그리드)
 └─ 기존 섹션 유지: 지금 가기 좋은 내 카드 / 내가 연 카드(필터) / 최근 방문 기록 / 전체보기
```

## 5. 프론트↔백엔드 연동 계약 초안

원칙: 프론트는 backend API만, 금액·캡·진행은 전부 서버 권위, 지급·배지·진행 기록은 멱등,
신규 테이블은 RLS deny-all + service_role(기존 마이그레이션 패턴 동일).

### 5.1 기존 API 변경

**GET `/api/cards/v2/today`** (응답 확장)

| 필드 | 변경 | 설명 |
|---|---|---|
| `dailyOpenLimit` | 의미 변경 | 고정 50 → 그날의 동적 캡 값. 기존 클라는 표시용으로만 사용하므로 하위 호환 |
| `openCap` | 신규 | `{ base: 50, effective, reason: 'daily_max'\|'regional_pool', regionLabel }` |
| `lockedCards[].slotType` | 신규 | `'category' \| 'mystery'`. mystery는 `category`·티저 카피 등 내용 단서 미포함 |
| `dailyLimit` | 의미 변경 | 150 → 동적 캡과 동일 값(티켓 1:1) |
| `collectionsSummary` | 신규(선택) | `{ activeSetCount, nearCompletion: { setId, title, filled, total } \| null }` — 홈 훅용 최소 요약 |

**POST `/api/cards/v2/open`** (응답 확장 — 요청은 변경 없음: `{ cardToken, adAttemptId }`)

| 필드 | 변경 | 설명 |
|---|---|---|
| `earned` | 의미 고정 | 항상 1 (필드 유지로 하위 호환) |

| `dailyOpenLimit`·`dailyLimit` | 의미 변경 | 동적 캡 값 |

**POST `/api/tickets/exchange/confirm`** (요청 확장)

- body: `{ exchangeId, grantResultKey?, paidAmount? }` — `paidAmount`는 SDK 지급 결과에서 얻은
  실지급 포인트(통계용). 서버는 sanity clamp 후 `paid_amount`에 기록. 미전달 시 NULL.

**GET `/api/tickets/config`** — `ticketsPerExchange=10` 유지. (광고 1회=1티켓 고정에 따라
클라 문구가 의존하는 값 변화 없음.)

### 5.2 신규 API (컬렉션)

| 엔드포인트 | 설명 |
|---|---|
| `GET /api/collections` | 활성 세트 목록 + 내 진행. 쿼리: `lat,lng`(지역 세트 필터). 응답 항목: `{ setId, slug, title, subtitle, tier, expiresAt, totalSlots, filledCount, slots: [ { slotIndex, state: 'filled'\|'empty', filled?: {카드 요약}, empty?: { hintText, silhouetteImageUrl } } ] }` |

## 7. 리스크 · 검수 체크

- **광고 정책**: 라이브 adGroupID만(`ait.v2.live.b50cf7d900884c5b` 유지, `__DEV__` 삼항 금지) ·
  `load→loaded→show` 순서 · reveal 후 자동 show 금지(뽑기 루프는 항상 명시 버튼) ·
  show 워치독/타임아웃 유지(ad-freeze 교훈) · 실돈(카드 공개·티켓) fail-closed 유지.
- **다크패턴**: 진입 광고시트·이탈방해 팝업 금지. 캡 도달은 명확한 종료 화면(추가 광고 유도 없음).
  "최대 금액" 과장 표기 금지 — 포인트 뽑기 금액은 평균·범위 중심으로 표기. 연속 루프가
  "한 번만 더" 압박이 되지 않게 게이지는 정보 제공형으로(카운트다운·타이머 압박 금지).
- **서버 권위·멱등**: 캡·티켓·컬렉션 진행·배지 전부 서버 계산/기록. 배지 unique(user_id, badge_key),
  진행 unique(user_id,set_id,slot_index), 교환 2-step confirm 멱등 유지. 클라 전달값은 `paidAmount`
  통계 필드 하나뿐(비권위 명시).
- **어뷰징**: 위치 스푸핑으로 동적 캡 상향 → 상한 50 + 티켓 가치 고정(광고 10회당 평균 20원)이라
  기대 이득이 광고 시청 노동보다 작다. 컬렉션은 금전 보상이 없어 어뷰징 유인 없음.
  꼬리 분포 큰 금액의 예산 소진은 콘솔 예산 상한 + 80% 소진 알림으로 방어(사용자 G5 설정).
- **스케일**: F_fresh 계산은 후보 수집 쿼리와 동일 필터의 COUNT — `/v2/today` 트랜잭션에 1쿼리 추가.
  하루 1회 고정 저장으로 반복 비용 없음. 세트 매칭은 open당 활성 세트 수(≤5)×슬롯 수(≤6) 소규모 대조.
- **TDS·문구**: 비게임 TDS 준수(컴포넌트 변형·커스텀 앱바 금지), 사용자 노출 문구 해요체.
  `DAILY_OPEN_LIMIT_REACHED`(캡)·pool_empty(풀 소진)·광고 없음 문구 3종 분리 유지.
- **하위 호환**: 구버전 클라는 `dailyOpenLimit`을 표시용으로만 쓰므로 동적 값이 내려가도 안전.
  `earned=1` 고정도 기존 필드 계약 안에서 동작. 배포 순서는 백엔드 선행(§8).

## 8. 전제조건 · 선행 과제

- **전시 공급 보강 (캡 인상의 선행 과제)**: 서울 전시 활성 59건·인천 0건, artmap 수집 하루 1건 수준.
  동적 캡이 정직해질수록 공급 부족 지역은 캡이 낮게 노출된다 — 전시 수집 소스 확충(별도 과제,

- 콘솔 랜덤 프로모션 설정(평균 20원 분포)·예산 = 사용자 G5 작업.

## 11. 작업 분해 · 슬라이스 순서 (작게 나눠 배포)

각 슬라이스는 독립 배포 가능하며 백엔드 선행 배포(하위 호환 유지) 후 프론트 번들 배포.

### S1. 경제 변경 (작음 — 즉시 배포 후보)
- **backend**: `randomTickets()` 제거 → 고정 1 · `DAILY_TICKET_LIMIT=DAILY_OPEN_LIMIT` ·
  `exchange/confirm`에 `paidAmount` 수용 + `paid_amount` 컬럼 마이그레이션 · 단위테스트(고정 지급·clamp 제거).
- **frontend**: reveal 티켓 연출 "+1" 고정 문구 · `exchangeTickets()`에서 지급 결과 금액 추출 시도 후
  confirm에 전달(§10-1 확인 결과 반영) · 티켓 게이지 10칸 표기.

### S2. 동적 오픈 캡 (백엔드 중심)
- **backend**: F_fresh COUNT 쿼리 + 캡 공식 + `user_tickets` 캡 컬럼 · `/v2/today`·`/v2/open` 응답에
  동적 `dailyOpenLimit`·`openCap` · `grantTicketsForEvent` 캡 강제 · 상향만 갱신 규칙 · 단위테스트
  (지역별 경계값·하루 고정·상향 갱신).
- **frontend**: 캡 도달 화면 `reason` 분기 문구(지역 프레이밍) · 진행 게이지가 동적 캡 표시.

### S3. 홈 연속 뽑기 + ? 슬롯
- **backend**: `slot_type` 마이그레이션 · ? 슬롯 공급 규칙(컬렉션 어시스트는 S4 전까지 탐험/와일드만) ·
  `/v2/today` mystery 응답 은닉 · `/v2/open`에 `reveal` 필드.
- **frontend**: 슬롯 프레젠테이션(2+?) · 연속 루프(다음 카드 뽑기 CTA·슬롯 재보충) · 히든/탐험 reveal
  연출 · "더 뽑기" 중복 이슈 정리. 광고 모듈 무변경 — 완료 후 민감로직 diff 검수(pitfall-audit §7).

### S4. 테마 컬렉션
- **backend**: 세트/슬롯/진행/배지 4테이블 마이그레이션(RLS deny-all) · 주간 생성 배치(slug 멱등) ·
  `/v2/open` 매칭·배지 지급(멱등) · 컬렉션 조회 API 3종 · teaser 활성 유지·조기 마감 처리 ·
  ? 슬롯 컬렉션 어시스트(60%) 활성화 · 단위테스트(매칭·멱등·조기마감).
- **frontend**: 컬렉션 탭 상단 세트 캐러셀 + 배지장 · 세트 상세 화면(실루엣+힌트) · reveal의
  컬렉션 채움/완성·배지 수여 연출 · 홈 `collectionsSummary` 훅.

### 게이트
- 각 슬라이스: qa-verify(`verify-miniapp.sh`) + pitfall-audit 선통과 → G3 기기 확인.
- G4 배포 승인(사용자) → S4까지 완료 후 release-preflight → G5 콘솔 업로드·프로모션 재설정(사용자).
